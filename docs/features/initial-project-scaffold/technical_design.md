# Technical Design: Initial Project Scaffold

## Inputs

- Product vision: `docs/product-vision.md`
- Deep Module Map: `docs/deep-module-map.md`
- Feature brief: `docs/features/initial-project-scaffold/feature_brief.md`
- Delegated skills: `clean-code`, `typescript`, `nextjs`, `postgresql-expert`, `ddd-hexagonal`

## Summary

Create the baseline RPGizer application with a modern Next.js scaffold using App Router, TypeScript, `src/`, Tailwind CSS, pnpm, PostgreSQL, Drizzle ORM, Drizzle migration tooling, Docker Compose for local Postgres, and a complete README. This feature establishes technical foundations only; it must not introduce auth, AI behavior, Adventure workflows, or product database tables.

## Existing Context

The repository currently contains planning docs and minimal project files only. There is no application scaffold, package manifest, Next.js app, database configuration, or meaningful README content beyond the project name.

## Proposed Design

### Scaffold Shape

Use the standard Next.js scaffold with these choices:

- App Router.
- TypeScript.
- `src/` directory.
- Tailwind CSS.
- ESLint.
- pnpm package management.

Expected top-level additions include:

- `package.json`
- `pnpm-lock.yaml`
- `next.config.*`
- `tsconfig.json`
- ESLint config generated by the scaffold or current Next.js defaults.
- Tailwind/PostCSS config if required by the selected Next.js/Tailwind version.
- `src/app/**` App Router files.

Do not add product modules under `src/modules/**` yet. The Deep Module Map should guide later product implementation, but this scaffold feature should not create empty module folders or speculative domain code.

### App Router and Landing Shell

Create a minimal RPGizer-branded landing shell in the default route.

Implementation direction:

- Keep `src/app/page.tsx` as a Server Component.
- Use Tailwind classes directly for the simple shell.
- Include enough visible RPGizer language to prove branding and styling work.
- Do not add Start Adventure, auth, Game Master chat, roadmap, or progression behavior.
- Keep `src/app/layout.tsx` focused on metadata, fonts if scaffolded, and the root HTML/body shell.

The landing shell is a scaffold validation surface, not binding UX for the product experience.

### Database Foundation

Configure PostgreSQL as the target database and Drizzle ORM as the database toolkit.

Add dependencies/tooling for:

- `drizzle-orm`
- Drizzle migration generation/application tooling.
- PostgreSQL driver package compatible with the chosen Drizzle setup.

Add a Drizzle config that reads `DATABASE_URL` from the environment and points migrations to a conventional migrations directory, such as `drizzle/`.

Do not add product tables or a product schema in this feature. If Drizzle requires a schema entrypoint, keep it intentionally empty or minimal without defining RPGizer product concepts. The first real migration should be introduced by the first persistence feature.

### Local PostgreSQL

Add Docker Compose support for local PostgreSQL with simple development defaults:

- user: `postgres`
- password: `postgres`
- database: `rpgizer`

Expose PostgreSQL on a predictable local port unless a later implementation identifies a conflict.

Add `.env.example` documenting the development `DATABASE_URL`. Do not commit `.env.local` or real secrets.

### Project Commands

Add clear package scripts for common workflows:

- local development
- production build
- start built app
- lint
- typecheck
- combined validation if useful
- database migration generation
- database migration application

Command names should be simple and discoverable. Prefer conventional names such as `dev`, `build`, `start`, `lint`, `typecheck`, `db:generate`, and `db:migrate` unless the scaffold tooling strongly suggests otherwise.

### README

Replace the minimal README with a complete project README covering:

- RPGizer overview.
- prerequisites: Node.js, pnpm, Docker.
- setup steps.
- environment variables and `.env.example`.
- starting local Postgres through Docker Compose.
- running the app locally.
- Drizzle migration generation/application commands.
- lint/typecheck/build/validation commands.
- where product and planning docs live.

The README should be accurate for a fresh checkout and should avoid documenting product flows that do not exist yet.

### Module Boundary Implications

This scaffold does not implement any Deep Module business behavior.

Boundary decisions for future work:

- `src/app/**` is the Next.js framework adapter boundary and should remain thin in future features.
- Future product behavior should live under the selected Deep Module boundary, likely `src/modules/<module-slug>/**`, following the DDD/Hexagonal guidance when backend behavior appears.
- Each module should own its own persistence needs; do not introduce a generic repository/database module.
- Database clients and Drizzle details should not leak into App Router pages or future business workflows.

## Validation

Implementation should verify:

- Dependencies install with pnpm.
- The Next.js dev server starts and serves the RPGizer landing shell.
- Tailwind styles are visibly applied.
- TypeScript typecheck passes.
- Lint passes.
- Production build succeeds.
- Docker Compose starts local PostgreSQL.
- Drizzle migration commands are present and can run against the configured local database without requiring product tables.
- README setup instructions match the actual commands.

## Risks / Tradeoffs

- Current Next.js and Tailwind scaffolds change over time; implementation should follow the generated defaults rather than fighting them.
- Drizzle configuration without product tables should stay minimal to avoid premature schema decisions.
- The landing shell should communicate RPGizer identity without becoming unreviewed product UX.
- Docker Compose defaults are development-only and must not be treated as production credentials.
